Findings

Ranked by impact on the failing metric

  1. Mobile LCP is poor on 30 of 32 pages Measured

    Median mobile LCP runs from 2.6 s (/invest-in-bonds) to 20.3 s (/collections/government-bonds), against a 2.5 s target. Most landing pages are between 6 and 9 s and most collections pages between 8 and 13 s. First Contentful Paint is 2.1–2.5 s on every page, so users see a blank page for about two seconds before anything paints. On desktop, 25 pages pass; five collections pages are poor at 4.4–5.7 s.

  2. The homepage HTML takes 3.4 s to finish arriving Measured

    Five plain curl requests for / each got the first byte in 0.15–0.25 s but the last byte at 3.38–3.46 s. The same test on /corporate-bonds finished in 0.60–0.71 s. In the Lighthouse traces the document request stays open for 3.5–8.5 s, and the hero paints 2.6–5.7 s after its image has already downloaded. In two of the six mobile runs the first byte itself took 2.1 s; in the other four it took 0.13–0.25 s. The server is streaming the page and holding the end of it on something slow.

    Fix: find the data call the homepage server render waits on and take it off the blocking path: cache it, or put the section that needs it behind its own Suspense boundary so the hero flushes first. The hero carries data-has-banner="true", so the banner lookup is the first place to check. That is an inference from the markup, not something the trace proves.

  3. One 138 KB stylesheet blocks rendering on every page Trace-backed

    /_next/static/chunks/087yhe5wlsb2s.css (138 KB) is render-blocking on all 32 pages, with an estimated 700–900 ms of First Contentful Paint to recover on each. Two to six smaller CSS chunks block alongside it. This is the floor under FCP and it delays every text LCP. It was 129 KB on 28 Sep.

    Fix: move page-specific styles out of the global bundle (CSS modules per route), inline critical above-the-fold CSS, and load the rest non-blocking. Check whether Tailwind's safelist or unused design-token blocks are inflating the bundle.

  4. Collections, FAQ, issuer and FD pages ship 5–8 MB of images Trace-backed

    All 11 collections pages transfer 5.9–7.6 MB, of which 4.7–6.3 MB is images. The sidebar collection art is the cause: Goverment.png 820 KB, refer-earn-gift.png 639 KB, high-rated-collection.png 600 KB, short-term.png 550 KB, Trophy.png 538 KB, plus SVGs of 0.5–0.8 MB each. Lighthouse estimates 2.5–3.6 MB could be saved per collections page. /faq (6.9 MB) and the issuer page (5.4 MB) load SVGs of up to 1.2 MB each from d35kx21znie3xm.cloudfront.net/images/. /fixed-deposits (4.8 MB) bundles gold-shield.svg at 1.1 MB and cal.svg at 1.0 MB in its own build. On slow 4G these downloads compete with the content that becomes LCP.

    Fix: re-export the collection art at display size as WebP or AVIF (tens of KB each). An SVG of 0.5–1.2 MB almost always has a bitmap embedded in it; export those as real vectors or as WebP. Serve CMS images through next/image so they are resized per device, and lazy-load everything below the first screen.

  5. Hero images get no fetch priority on 14 pages Trace-backed

    The LCP discovery check fails on every page with an image LCP except the homepage. The hero <img> on Corporate Bonds, Fixed Deposits, NCD IPO, Sovereign Gold Bond, Government Securities and Better-than-FDs has no fetchpriority, and the browser waited 1.4 s (FD) and 3.1 s (G-Sec) before starting the download. The Careers hero is a CSS background that is not in the HTML at all. On /collections/government-bonds and /collections/tax-free-bonds the banner that becomes LCP is lazy-loaded.

    Fix: add priority to each hero next/image (or fetchpriority="high" on a plain <img>), as the homepage now does. Render the Careers hero as an image element. Remove loading="lazy" from the first collections banner.

  6. One layout shift of 0.087 repeats on 29 of 32 pages Trace-backed

    On mobile the whole main#main-content block moves once, scoring 0.087, on every page except Signup, Invest in Bonds and the IPO detail page. The same shift scores 0.033–0.041 on desktop. It is one shift of the same element every time, which points to something being inserted above the main content after first paint. It passes today with 0.013 to spare, so any second shift pushes a page over. /collections/public-sector-bank-bonds already reaches 0.102 on desktop.

    Fix: record a trace on one page, find what is added above main, and reserve its height in the server-rendered HTML. Fixing it once in the shared layout clears all 29 pages.

  7. S3 and CloudFront images are served with no cache lifetime Trace-backed

    Lighthouse flags cache policy on 30 of 32 pages. Images from s3.ap-south-1.amazonaws.com/production.goldenpi.com and d35kx21znie3xm.cloudfront.net, including the homepage hero banner, come back with a cache lifetime of zero. On collections pages that is 4.5–6.1 MB fetched again on every visit.

    Fix: set Cache-Control: public, max-age=31536000, immutable on versioned assets in both buckets, or a shorter lifetime with revalidation where file names are reused.

  8. 130–150 KB of unused JavaScript on every page Lighthouse estimate

    Most pages transfer 746–809 KB of JavaScript, of which Lighthouse estimates 131–152 KB is never run during load. /contact-us is the outlier at 1.6 MB: it loads Google reCAPTCHA (355 KB, 188 KB unused) up front, along with a Roboto font that has no font-display. Blocking time still passes, so this costs download time more than responsiveness.

    Fix: load reCAPTCHA when the contact form is focused, not on page load. Check the shared chunk 2cd3sg-d1ayj5.js (133 KB, 59 KB unused) for components that can be dynamically imported.

  9. Smaller items Trace-backed

    Images without width and height on 12 pages, ten of them issuer logos on /investment-options/list-view. Forced reflow during load on the list view and four collections pages. Main-thread work is 1.3–4.8 s on mobile, mostly style, layout and script evaluation, without long blocking tasks.

Method

Test conditions

Pages
32 routes on uatnew.goldenpi.com, logged out, with the gp-locale=en cookie (without it, / redirects to itself)
Mobile
Lighthouse default: 412×823 at 1.75× DPR, simulated slow 4G (150 ms RTT, 1.6 Mbps), 4× CPU slowdown, cold cache, 3 runs (6 on the homepage), median by metric
Desktop
Lighthouse desktop preset: 1350×940, 40 ms RTT, 10 Mbps, no CPU slowdown, 1 run
INP
Playwright on Chromium, 412×823 touch emulation, 4× CPU throttle, Event Timing entries per tap, taps made after the page settled
Server timing
curl with compression, 5 requests each for / and /corporate-bonds
Host
macOS, headless Chrome for Testing, one run at a time
  • UAT data changes often. Bond, FD and IPO rows are client-fetched, so page weight and LCP on listing pages vary with what is live on the day.
  • Several pages have a wide LCP range across their three runs (for example 4.1–21.3 s on /collections/government-bonds). Read the median with its range, not as a fixed value.
  • Lighthouse scores are summaries whose weighting changes between versions. Compare the metric values, not the score.
  • The savings quoted above are Lighthouse estimates, not measured gains. Re-run the same three-run mobile median after each fix to confirm.
