Findings

Ranked by impact on the failing metric

  1. Mobile LCP is poor on 5 of 8 pages Measured

    On a first visit the logged-in listing pages are slower than their guest versions: Corporate Bonds 12.2 s (guest 8.1 s), Fixed Deposits 10.3 s (guest 8.6 s), NCD IPO 8.7 s (guest 7.6 s). Explore is at 10.4 s and Notifications at 10.2 s. First Contentful Paint is 2.0–2.3 s on every page. With a warm cache the same pages come in at 2.9–4.5 s, which is still over the 2.5 s target.

  2. The LCP image is added by JavaScript, late and without priority Trace-backed

    On five pages the largest element is an image that is not in the server HTML, so the browser cannot start it until the app has booted: the post-login banner on Explore (download starts 1.7 s late), the app-download promo on Fixed Deposits (2.1 s) and NCD IPO, the Bond Utsav promo on Corporate Bonds (1.4 s, then 1.0 s to download), and the empty-state illustration on Notifications. None has a fetch priority, and three of them are lazy-loaded.

    Fix: server-render the first banner or promo with its image URL, mark it priority, and drop loading="lazy" on it. Where the largest element is decoration (the Notifications empty state), size it down so the heading becomes the LCP.

  3. Layout shifts fail on five pages Trace-backed

    /profile/orders scores 0.276 on all three runs: the order history section (section.orders-page__history) moves by 0.189 when orders arrive, on top of the 0.087 shift of main#main-content that every page shares. /user/fixed-deposits reaches 0.194 when #explore-fds shifts by 0.103, and /user/bond-ipo-online reaches 0.203 when #explore-ipos shifts by 0.116. Profile (0.104) and Notifications (0.103) are pushed over the limit by the shared shift plus one small shift of their own. On desktop, /profile scores 0.234 from a single shift of the whole main block.

    Fix: give the orders list, the FD list and the IPO list a skeleton with the same height as the loaded rows, so data arriving does not push content. Fix the shared main shift once in the layout, as in the guest report.

  4. /user/bond-ipo-online never settles Trace-backed

    All four cold runs and the warm run of this page hit Lighthouse's 60-second trace limit, with 35–37 s of main-thread work on mobile. The guest /bond-ipo-online settles in about 4 s with 3.3 s of work. Explore and logged-in Corporate Bonds did the same in one of their three runs each. Blocking time stays low (139 ms), so this is steady background work and not long tasks: it will not show in INP, but it keeps a phone's CPU busy for as long as the page is open.

    Fix: record a performance trace on the page for 30 seconds after load and look for a timer, polling request or animation that never stops. In two of the runs the page also requested two bond detail routes that returned 502, so check whether those are being retried. That last point is a lead from the network log, not a proven cause.

  5. The same 138 KB stylesheet blocks rendering Trace-backed

    /_next/static/chunks/087yhe5wlsb2s.css is render-blocking on all 8 pages, with an estimated 710–890 ms of First Contentful Paint to recover on each. The fix is the one in the guest report.

  6. Requests fail while the pages load Measured

    On every load of /user/explore, /api/gpi/v0/cms/get-faqs returns 400 five times and /api/gpi/v0/landing-page/fetch-json-data returns 500 once. /user/corporate-bonds gets one 400 from get-faqs per load. In two of its four runs, /user/bond-ipo-online requested two bond detail routes that returned 502. During the pass, /user/notifications itself returned 502 on three attempts in a row, then loaded normally a few minutes later.

    Fix: these are functional bugs more than performance ones, but each failed call is a wasted round trip on slow 4G. Fix the get-faqs request parameters and stop calling it five times per page.

  7. Logged-in pages load 300 KB of tag-manager script Trace-backed

    Google Tag Manager and gtag add 301 KB on every logged-in page; the guest pages did not load them in the lab. JavaScript is 0.8–1.3 MB per page against 0.75–0.81 MB for guests, and Lighthouse estimates 127–348 KB of it goes unused during load.

    Fix: load the tag manager after the page is interactive, and review which tags the container fires on account pages.

  8. The portfolio was tested at the wrong address Measured

    /portfolio returns the not-found screen on UAT, logged in or out, which is why it rendered 58 elements and no portfolio request. The portfolio lives at /profile/portfolio. That route still needs a full three-run pass with a fresh login.

Method

Test conditions

Pages
8 routes on uatnew.goldenpi.com, logged in with a saved UAT test session. Each run was confirmed signed in by a 200 from customer/get-profile.
Mobile
Lighthouse default: 412×823 at 1.75× DPR, simulated slow 4G (150 ms RTT, 1.6 Mbps), 4× CPU slowdown, 3 runs, median by metric. Lighthouse attached to a logged-in headless Chrome; cookies and storage kept, HTTP cache emptied before every run.
Repeat visit
Same setup without emptying the cache, 3 runs
Desktop
Lighthouse desktop preset: 1350×940, 40 ms RTT, 10 Mbps, no CPU slowdown, cold cache, 1 run
INP
Playwright on Chromium, 412×823 touch emulation, 4× CPU throttle, Event Timing entries per tap, taps made after the page settled
Host
macOS, headless Chrome for Testing, one run at a time
